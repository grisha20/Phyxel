# Отдельные элементы и устанавливаемые пакеты

Дата: 2026-10-03. Архитектурное направление, не реализованный магазин.

## Что уже существует

Каждая из20 записей core описана отдельным `Materials/core/<id>.json`.
Её человеческий паспорт находится в `docs/materials/name/PASSPORT.md`
для `core:name`, либо `docs/materials/namespace__name/PASSPORT.md` для
другого namespace; паспорт не
загружается физическим решателем. Общие алгоритмы расположены в C#/HLSL:
сыпучие, жидкости, тела, тепло, фазы, горение, газ/воздух и реакции.

[MaterialFileLoader](../../../Materials/MaterialFileLoader.cs) читает внешние
`*.json` рекурсивно. [MaterialRegistry](../../../Materials/MaterialRegistry.cs)
загружает их при создании реестра, проверяет ID и ссылки; внешний материал
не может объявлять `core:*` или заменять встроенный ID. Путь задаётся
`PHYXEL_MATERIALS_PATH`, по умолчанию `AppContext.BaseDirectory/Materials`.
Горячая установка в уже работающую симуляцию этим не подтверждается.

Ссылки между материалами используют стабильные ID; RuntimeIndex назначается
при запуске и не может служить постоянным ключом купленного элемента.

## Что означает «один элемент — один файл»

Данные вещества можно хранить в отдельном JSON, а общую физику использовать
повторно. Это уже сделано. Например, похожие негорючие порошки могут
различаться плотностью/трением/цветом без копии шейдера.

Новое поведение, которого нет в схеме или решателе, нельзя получить одними
числами. Растворение, электричество, новый состав смеси или разрушение
потребуют общего механизма и обновления схемы/движка. После появления такого
механизма его смогут использовать разные элементы. Не создавать отдельную
копию физического движка на каждое платное вещество.

## Предлагаемый контракт пакета

| Часть | Что хранит | Сейчас |
|---|---|---|
| Манифест | Стабильный package ID, версия, совместимая версия движка/схемы, зависимости и список материалов | Специального пакета не реализовано |
| Материалы | Отдельные JSON с ID вида `author:name`, переходами и продуктами по ID | Внешний JSON loader существует |
| Оформление | Текстуры/иконки/локализация с устойчивыми путями | Автономный формат пакета ресурсов не подтверждён текущим loader |
| Доступ | Получено право на пакет и разрешено его создание в редакторе | Учёт покупки/лицензии не реализован |
| Регистрация | Проверка схемы, зависимостей, уникальности ID и доступности механизмов | Часть проверок есть; manifest/version resolver отсутствует |
| Проверки | Паспорт, пары взаимодействий, воспроизводимые acceptance-сцены | Workflow и паспорта есть; выпуск пакетов не автоматизирован |

Покупка может выдавать право установки/использования пакета. Доставка JSON
сама по себе не является системой проверки права. Не обещать защиту простой
проверкой наличия файла. Детали аккаунта/магазина выбираются позже; сейчас
достаточно не связывать физику с платёжным провайдером.

## Сохранения — обязательная часть будущего формата

[SimulationStateSerializer](../../../Serialization/SimulationStateSerializer.cs)
уже хранит палитру ID и сопоставляет её с реестром. **Сейчас отсутствующий ID
заменяется на `core:empty` с предупреждением**. Для устанавливаемых/платных
пакетов такой fallback нельзя считать законченной совместимостью: сцена
после перезаписи может потерять материал.

Будущий контракт: до применения мира определить все отсутствующие пакеты,
сохранить исходный файл и предложить установить зависимости. Если открыть
мир без пакета невозможно корректно, не продолжать разрушительную загрузку
и не перезаписывать оригинал. Вопрос просмотра сцен с некупленным пакетом
решается отдельно: возможен зарегистрированный read-only просмотр без
права рисовать элемент, но такого режима сейчас нет.

В сцене нужны package ID/версии и зависимости в дополнение к material ID.
Обновление пакета не должно молча менять старое вещество до несовместимого
поведения; потребуются правила миграции/версий. Эти изменения делать
отдельным этапом после доведения существующего каталога.

## Очерёдность

1. Довести общие механизмы и текущие взаимодействия по [плану](ROADMAP.md).
2. Проверить внешний тестовый элемент на существующих механизмах.
3. Ввести manifest, зависимости, совместимость и безопасную загрузку мира.
4. Затем добавить установку пакетов, учёт доступа и интерфейс магазина.

План не требует превращать существующие встроенные core ID в платные.
Состав бесплатного ядра и продаваемых дополнений — отдельное решение продукта.

## Дополнительный общий механизм moisture

В схеме1 необязательный блок: `liquid`, `dry`, `wet` (string ID), `capacity`, `absorptionRate`, `dryingRate` (положительные конечные игровые числа ≤10). Источник и dry/wet — granular с одинаковым moisture-блоком и сухой теплоёмкостью; dry горючий. Liquid должна поддерживать обратимую фазу пара с энтальпией. Core зависит только от core; external ссылки валидируются после стабилизации каталога. Старые JSON без блока работают как прежде. Настоящая влага сохраняется в клетке v12; один новый JSON сам по себе не добавляет химию/новый движок.
