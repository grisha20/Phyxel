## 3. Что уже реализовано и что это действительно подтверждает

**Два режима:** «Песочница» — горение без обязательного подвода фонового
кислорода; «Симуляция» — конечный кислород, его перенос и расход.
«Гидравлика сосудов» — отдельная настройка жидкости, не третья модель
горения. «Гравитация построек» тоже отдельна: свободный лёд/застывшее масло
двигаются независимо от неподвижных печных стен.

**Масло:** выбран парафиновый представитель n-гексадекан; это не бензин
и не универсальная модель всех масел. В текущем JSON: плотность 0.8,
вода 1; замерзание 18°C, кипение 287°C, температурный поджиг 205°C,
контактный 135°C. Мобильность зависит от температуры, опорная T20°C.
Прочти паспорт для происхождения/ограничений чисел. Масляный пар и
застывшая фаза существуют. Wood/coal/wet_charcoal хранят масляную пропитку
FuelMass, которая расходуется как дополнительное топливо; влажность

## 5. Проверки и запуск

Начни с собственных воспроизводимых случаев по новым видео и коротких
замеров. Затем выбери существующие проверки по затронутому механизму.
Не запускай весь каталог без причины. Прочитай параметры runner перед
запуском: некоторые имеют старый жёсткий формат сцены и baseline.

Из корня проекта, PowerShell:

```powershell
dotnet build --no-restore
./Diagnostics/RunLiquidLayers.ps1 -Matrix -Show -ArtifactRoot artifacts/handoff-20261005/layers
./Diagnostics/RunLiquidTemperature.ps1 -ArtifactRoot artifacts/handoff-20261005/temperature
./Diagnostics/RunWaterLevel.ps1 -ArtifactRoot artifacts/handoff-20261005/water
./Diagnostics/RunOilLocality.ps1 -Mobile -ArtifactRoot artifacts/handoff-20261005/locality
./Diagnostics/RunOilSmokeFlow.ps1 -Cases oil -Matrix -Show -ArtifactRoot artifacts/handoff-20261005/oil
./Diagnostics/RunFirePerformance.ps1 -Seconds 10 -Radius 5 -ArtifactRoot artifacts/handoff-20261005/fire-performance
```

Это список доступных команд, не поручение запускать всё автоматически.
Для масла/пропитки есть `RunOilPhases.ps1`, `RunOilAbsorption.ps1`,
`RunOil.ps1`; для газов — `RunOpenCombustion.ps1`, `RunGasFlow.ps1` и
другие gas runners. Для печи — `Diagnostics/SavedFurnaceAcceptance.cs`,
`RunSandboxFurnace.ps1`; старый сценарий требует 672×378/старый формат,
поэтому не применяй его к новой сцене вслепую. Курсор также имеет
`Diagnostics/TemperatureProbeAcceptanceTrace.cs` и UI regression tests.
Water performance потребует отдельного воспроизводимого измерения:
fire-performance не заменяет такой тест.

GPU тесты запускай **последовательно**. Не собирай проект, пока запущен
Phyxel: сначала дождись завершения своего процесса. Не закрывай
пользовательский несохранённый мир ради сборки. Долгие тесты должны
показывать живую сцену и не блокировать Windows message loop.
LL/OS `-Show` рисуют через Update/Draw, Escape отменяет; остальные старые
runners часто скрытые и блокирующие — не называй их визуальными.
`Diagnostics/WarmCellularShader.ps1` готовит дорогой клеточный шейдер
до открытия тестового окна. Одна компиляция может занять несколько минут;
не запускай несколько одинаковых компиляций одновременно.

LL ускоряет матрицу пакетами 16 логических шагов на UI update. Это не
видео реального темпа. Для жалоб на скорость используй обычный игровой
режим и wall-clock измерения. PASS старого теста не отменяет нового видео.

## 6. Постоянные правила и предпочтения пользователя

- Сначала источники → паспорт/контракт → реализация → измерения →
  актуализация паспортов, индекса и затронутых строк карты пар.
  Не требуй отдельного подтверждения паспорта: исправления уже поручены.
- Активно читай исходники TPT, включая общие обработчики. Отличай код
  Phyxel, код TPT, реальную физику, выбранную игровую модель и будущие идеи.
- Пользователю нужен приятный, понятный и активный огонь: горячее пламя
  ярче, бело-жёлтое у горячего источника, краснеющее при охлаждении;
  TPT — ориентир. Дым не должен выглядеть крупицами с эффектами.
- При хорошей тяге поток занимает существенную ширину трубы и ускоряется.
  Не «успокаивай» печь общим замедлением всех газов. Первоначальный выброс
  из нижнего отверстия допустим; после розжига ожидается устойчивый выход
  вверх. Уголь должен реально расходоваться и менять форму с горящей стороны.
- Песочница должна позволять играть без обязательного знания кислородного
  поддува. В Симуляции сохраняются конечный кислород, охлаждение, влажность
  и физические ограничения. Не стирай различие режимов глобальным обходом.
- Масло впитывается медленнее воды; масляная пропитка усиливает горение
  подходящего материала и визуально заметна. Влага и масло — разные запасы.
- Плотность сравнивается с конкретной жидкостью. Свободное зерно, плотная
  куча, плавающее тело и неподвижная постройка — разные случаи. Не возвращай
  баг, при котором контакт струи с углём вытаскивает кучу через маленькую
  дырку, либо тяжёлое покрытие остаётся неподвижной шапкой на воде.
- Температурная вязкость, теплообмен, оплаченные фазовые переходы и
  сохранения уже существуют. Не подменяй их декоративными цветами,
  исчезновением массы/CO₂, бесконечным топливом или бесплатной энергией.
- Критерии acceptance зафиксировать до итоговых тестов. Не ослаблять пороги
  после FAIL и не увеличивать ожидание только ради PASS. Сравнивать до/после;
  динамику при 30/60/100FPS — по одинаковому физическому времени.
- Не обязателен повтор всех проверок при каждом изменении. Выбирай
  затронутые проверки; расширяй при конкретном сбое или неопределённости.
  Пользователь просил работать результативнее, без лишних многократных прогонов.
- Общий механизм делать по свойствам/kind/flags/density, не по runtime ID
  и не копией шейдера на каждый элемент. Исключения миграции документировать.
- Паспорта служат основой для будущих веществ и повторного использования
  механизмов. Будущие донат-элементы и живое растущее дерево пока идеи,
  не задача этого этапа.
- Отчёты короткие, по-русски: что исправлено, что проверено, что осталось.
  Во время долгой работы давать понятные обновления, не пропадать молча.
- По завершении этапа **commit с понятным названием и обычный push текущей
  ветки в origin обязательны**; это постоянное поручение, подтверждение не
  нужно. Без force push, сборок, диагностических артефактов и Python-кеша.
  Сохраняй чужие изменения. Новые задачи/сообщения в другие чаты не создавать
  без отдельного поручения; пользователь сам передаёт этот промпт.

Начинай с видео и проверки рабочего состояния. Затем веди таблицу пяти
проблем: воспроизведение → причина → исправление → проверка. Заверши все
пять либо честно укажи конкретный оставшийся блокер. Не объявляй весь
этап завершённым по одному удачному простому сценарию.
