# Дорожная карта: Phyxel → «TPT, только лучше»

Файл живой. Отмечай `[x]` по мере выполнения. Каждый этап заканчивается коммитом
и зелёным гейтом регрессии.

**Целевой охват:** классическое ядро TPT — порошки, жидкости, газы, температура,
огонь/взрывы, поле давления и воздуха, плавление/растворение, ~60-80 элементов.
Электроника, фотоны/нейтроны и ньютоновская гравитация — вне текущего плана.

**Роли:** Claude пишет код и даёт точные команды. Степан запускает на Windows/DX11
и присылает вывод. Claude разбирает и правит.

---

## Железные правила (нарушение = откат)

1. **Вода неприкосновенна.** Функции `PlanWaterColumnMove`, `RelaxWaterPressureRoute`,
   `PlanPressurizedWaterMove/Return`, `ApplyPressurizedWater*`, `ResolveOrdinaryWater*`,
   `ResolveOrdinarySurface*`, `ResolveWaterColumnSpan`, `BuildWaterColumnInfo`,
   `FindOrdinaryWaterDestination`, `WaterPathClear/Filled*` не редактируются.
   Новая физика подключается **рядом**, а не вместо.
2. **Всё новое — за флагом.** Каждая новая подсистема получает выключатель в
   `SimulationSettings` и по умолчанию **выключена**, пока этап не закрыт.
3. **Layout меняется парой.** `Physics/PhysicsDataStructures.cs` и
   `Content/Shaders/PhysicsShared.hlsli` правятся в одном коммите. Рассинхрон
   не даёт ошибки компиляции — он тихо портит данные.
4. **Serialization не трогаем** до этапа, где явно поднимается версия формата.
5. **Один этап — один коммит.** Не смешивать. Откат должен быть дешёвым.
6. **Перед каждым коммитом — гейт воды** (см. Этап 0).

## Этап 2. Разделение `density` и `weight`

**Проблема:** одно число `density` отвечает сразу за плавучесть, порядок газов
и granular-поведение. В TPT это разные свойства (`Weight` — кто кого вытесняет,
плотность/`Gravity` — как падает). Отсюда невозможность настроить элемент,
не сломав что-то другое.

- [ ] 2.1 Добавить `physics.weight` в JSON-схему. Если не указан — `weight = density`
      (полная обратная совместимость, ни один существующий материал не меняется).
- [ ] 2.2 Добавить `Weight` в `MaterialProperties` (C# + HLSLI, один коммит).
- [ ] 2.3 В правилах вытеснения (`GranularCanDisplaceLiquid`, `CanMoveSand`,
      обмены granular↔liquid) использовать `Weight` вместо `Density`.
      **Водные функции не трогаем** — там `Density` остаётся.
- [ ] 2.4 Оставить `Density` для термики, плавучести и порядка слоёв газа.
- [ ] 2.5 Гейт воды — обязан быть 1:1 с baseline, так как по умолчанию
      `weight == density` и поведение не должно измениться ни на пиксель.

**Файлы:** `Physics/PhysicsDataStructures.cs`, `Content/Shaders/PhysicsShared.hlsli`,
`Materials/MaterialFileLoader.cs`, `Materials/MaterialRegistry.cs`,
`Content/Shaders/CellularAutomataSolver.hlsl` (только granular-функции).
**Не трогать:** водные фазы, `Serialization/`.
**Риск:** высокий по layout — обязательна сверка размеров структур.
**Готово когда:** гейт байт-в-байт совпадает с baseline, а `weight` уже можно
задавать в JSON.

## Этап 3. Поле воздуха — расчёт и визуализация

**Ядро всего плана.** В TPT есть поле на грубой сетке (`CELL = 4`): давление `pv`,
скорость `vx/vy`, температура воздуха `hv`. Из него растут взрывы, разлёт газа,
вентиляторы, ударные волны. У Phyxel `GridCell.Pressure` — это счётчик кадров
приземления, а не давление. Настоящего поля нет.

**На этом этапе поле только считается и рисуется. К движению не подключается.**

- [ ] 3.1 Новый шейдер `Content/Shaders/AirSimulation.hlsl`, сетка `Width/4 × Height/4`.
      Буферы: `AirPressure`, `AirVelocityX`, `AirVelocityY`, `AirAmbientHeat`.
- [ ] 3.2 Проход адвекции (semi-Lagrangian) + диффузии (3×3 гауссово ядро,
      как `Air::make_kernel`) + затухания.
      Константы по образцу TPT: `TSTEPP 0.3`, `TSTEPV 0.4`, `VADV 0.3`,
      `VLOSS 0.999`, `PLOSS 0.9999` — стартовые значения, потом тюним.
- [ ] 3.3 Стены: твёрдые клетки блокируют поток (аналог `bmap_blockair`).
      Строится по уже существующей `CellMaterials`-карте.
- [ ] 3.4 `Graphics/AirSimulationResources.cs` + диспатч в координаторе.
      Флаг `SimulationSettings.AirSimulation`, по умолчанию **выключен**.
- [ ] 3.5 Режимы отображения в `RenderComposition.hlsl`: `Pressure`, `Velocity`,
      `AirTemperature` (как клавиши отображения в TPT). Переключение из UI.
- [ ] 3.6 Диагностический сценарий `air_smoke`: точечный импульс давления,
      проверить что волна расходится, затухает и отражается от стен.
- [ ] 3.7 Замер GPU-времени, как уже сделано для газа/термики.

**Файлы:** новые `AirSimulation.hlsl`, `Graphics/AirSimulationResources.cs`;
правки `SimulationDispatchCoordinator.cs`, `RenderComposition.hlsl`,
`Core/SimulationSettings.cs`, `UI/`.
**Не трогать:** `CellularAutomataSolver.hlsl` вообще.
**Риск:** низкий для существующей физики (флаг выключен), средний по производительности.
**Готово когда:** видно красивое поле давления, вода не изменилась.

- [ ] 4.1 Свойство материала `hotAir` (аналог `Element::HotAir`): горячие

- [ ] 4.2 Свойства `advection`, `airDrag`, `airLoss` в JSON.
- [ ] 4.3 `GasRedistribution.hlsl`: скорость из поля воздуха добавляется
      к переносу массы газа. Плотностная сортировка остаётся.
- [ ] 4.4 Огонь (`flags: flame`) перестаёт быть полностью отдельным: он движется
      воздухом и сам греет воздух. Собственный lifetime сохраняется.
- [ ] 4.5 Дым, CO₂, пар получают `advection`/`airDrag` — должны наконец
      клубиться и закручиваться, а не просто всплывать.
- [ ] 4.6 Визуальная проверка: костёр даёт восходящий поток, дым уносит вбок

## Этап 6. Единый параметрический движок движения

Самое глубокое изменение. Делаем **параллельный** путь, не заменяя существующий.

- [ ] 6.1 Новый шейдер `UnifiedMotion.hlsl`: один кернел «попробовать сдвинуться

      Аналог `Simulation::try_move` / `eval_move` из TPT.
- [ ] 6.2 Флаг материала `unified-motion`. Материалы **по одному** переводятся
      на новый движок. Вода и песок — **последние в очереди**, если вообще.
- [ ] 6.3 Порядок перевода: дым → CO₂ → пар → огонь → уголь → порох → новые порошки.
- [ ] 6.4 После каждого переведённого материала — гейт воды + визуальная проверка.
- [ ] 6.5 Решение по воде принимается **отдельно** и только если новый движок
      объективно лучше на сравнительных сценариях. По умолчанию вода остаётся
      на своём выверенном солвере навсегда — это нормально.

**Риск:** высокий, но изолированный флагом. Любой материал можно вернуть обратно

## Известные ограничения, принятые осознанно

- Вода остаётся на собственном специализированном солвере. Это не долг,
  это осознанное решение: она работает и на неё потрачено много времени.
- Одна клетка = один материал. Настоящих смесей нет и не планируется.
- Электроника, фотоны/нейтроны, ньютоновская гравитация — вне плана.
